# 预约并发控制与数据一致性（Day 11–12）

## 1. 目标与边界

预约链路要解决的核心问题：**同一研修室的同一时段，并发下只能成功一次**。

方案分两层：

| 层 | 手段 | 作用 |
|---|---|---|
| Redis（前置闸门） | Lua 原子占位 + 幂等键 | 毫秒级拦掉"已满"与"重复提交"，减少打到数据库的请求 |
| MySQL（最终防线） | 条件更新 + CHECK + 唯一键 | 任何情况下都不超卖、不重复落库 |

一句话边界：**一致性由数据库提供，Redis 只提供拦截率。** 因此 Redis 不可用时降级放行是安全的；反之，把 Redis 计数当成权威账本才是错的。

## 2. 链路顺序

```
validateCreateRequest
  → loadBookableSlot（只读：取 booking_capacity，并构造 key）
  → ① guard.tryAcquire      幂等占位  SET NX  PROCESSING:{token}
  → ② guard.tryOccupy       时段占位  Lua: HEXISTS → HGET n → HINCRBY + HSET + EXPIRE
  → ③ reservationTxService.create   事务内：user 行锁 → 幂等复查 → 时段校验 → 重叠校验 → tryOccupy → insert
  → ④ guard.markDone        回写终态  SET  DONE:{reservationId}
失败（事务返回之后）:
  → guard.release(slotKey)  释放时段占位
  → guard.clear(idemKey)    删除幂等键
```

排序判据：**能回滚的在前，不可回滚的在后。** Redis 占位失败只是少拦一次请求；数据库写入失败必须补偿 Redis，否则名额会被锁到 TTL 到期。

为什么不能反过来先写库再占 Redis：库一提交库存就扣了，Redis 变成事后缓存，一个请求都拦不住。

## 3. Key 规范

| 用途 | 格式 | TTL |
|---|---|---|
| 时段占位 | `slot:{resourceId}:{yyyy-MM-dd}:{HH:mm}:{HH:mm}` | 300 秒（`slot-ttl-seconds`） |
| 幂等（处理中） | `reservation:idempotent:{userId}:{requestId}` | 60 秒（`processing-ttl-seconds`） |
| 幂等（已完成） | 同上，value 为 `DONE:{reservationId}` | 86400 秒（`idempotent-ttl-seconds`） |

三条硬约束：

1. **必须带日期。** 任务模板 `resource:{id}:slot:{startTime}:{endTime}` 漏了日期，10/28 与 10/29 的同一时段会拼成同一个 key，第二天直接"已满"。
2. **一律由 `ResourceSlot` 实体构造**（`ReservationKeys.slot(slot)`），不信任前端传的时间。
3. **时间格式固定 `HH:mm`。** `LocalTime.toString()` 在秒为 0 时输出 `14:00`、秒不为 0 时输出 `14:00:30`，同一时段会生成两种 key，闸门直接失效。

占位 value 用单个 Hash：

```
slot:{...}  →  n            : 已占数量
               o:{userId:requestId} : 持有者标记
```

计数与持有者放在同一个 key 里，才能用一个脚本原子地完成"校验 owner → 递减 → 计数归零则删除"。

## 4. Lua 脚本契约

### 4.1 `slot_occupy.lua`

```
KEYS[1] = slot key
ARGV[1] = capacity    ARGV[2] = owner token    ARGV[3] = ttl 秒
返回  0 成功 / 1 已满 / 2 已持有 / 3 参数错
```

执行顺序不能变：

1. `HEXISTS o:{owner}` 命中返回 2 —— 同一请求重复占位，不能把 `n` 加两次；
2. `HGET n` 与容量比较，够了返回 1；
3. `HINCRBY n` + `HSET o:{owner}` + `EXPIRE` 连续做完。

细节：`HGET` 在字段不存在时返回 `false` 而不是 `"0"`，必须 `tonumber(... or '0')`；`EXPIRE` 放最后，只有写成功才落 TTL。

为什么不能 `GET` 再 `SET`：检查与占位是两步，中间可插入其他请求，超卖就发生在这一瞬。Lua 在 Redis 内整体执行，期间不切入别的命令。

### 4.2 `slot_release.lua`

```
KEYS[1] = slot key    ARGV[1] = owner token
返回  1 释放成功 / 0 不是持有者
```

必须先 `HEXISTS` 校验 owner 再删。不校验直接 `DEL` 或 `HINCRBY -1`，A 请求超时释放时会把 B 刚抢到的占位一起清掉，照样超卖。计数减到 0 时 `DEL` 整个 key，避免残留空 Hash。

### 4.3 为什么必须用 `StringRedisTemplate`

`RedisConfig` 里现有的 `RedisTemplate<String, Object>` 使用 JSON 序列化，执行 Lua 时 `ARGV` 会变成带引号的 `"300"`，脚本里 `tonumber` 得到 `nil`，一路返回 3。因此闸门单独使用 `StringRedisTemplate`。

## 5. 事务边界

| 类 | 是否有事务 | 职责 |
|---|---|---|
| `ReservationServiceImpl#createReservation` | 否 | 编排：幂等占位 → 时段占位 → 调事务方法 → 成功回写 / 失败补偿 |
| `ReservationTxService#create` | `@Transactional` | user 行锁、幂等复查、时段校验、重叠校验、`tryOccupy`、`insert` |

两个必须知道的点：

1. **必须拆成两个 Bean。** 同类里 `this.create()` 不走 Spring 代理，`@Transactional` 不生效。
2. **释放不能写在事务内的 `finally`。** 那样释放发生在 commit/rollback 之前：别人抢进刚被"释放"的位置，随后你回滚，名额又还回来，直接双占。

成功路径**不释放**占位：占位随 TTL 自然过期。代价是 TTL 到期后 Redis 计数归零，闸门对该时段的拦截率下降，请求继续由数据库兜住——正确性不受影响。

## 6. 失败与降级

`application.yml` 中的开关：`resourceflow.reservation.redis.enabled`（当前默认 `false`，需要时手动打开）。

| 方法 | Redis 异常时 | 原因 |
|---|---|---|
| `tryAcquire` | 返回 `DEGRADED`，继续走库 | 幂等由 `uk_reservations_user_request` 兜底 |
| `tryOccupy` | 返回 `DEGRADED`，继续走库 | 超卖由 `tryOccupy` 条件更新 + CHECK 兜底 |
| `release` / `clear` | 吞异常，记日志 | 释放失败没理由让用户看到 500，最坏等 TTL |
| `markDone` | 失败仅记日志 | 不影响本次预约结果 |

降级只降性能，不降一致性——因为一致性从来不是 Redis 给的。

三种 TTL 各自的意义：

- `processing-ttl-seconds = 60`：只覆盖单次请求耗时。进程被 kill 时最多锁用户 1 分钟，而不是一天。
- `slot-ttl-seconds = 300`：占位兜底，释放失败时靠它自愈。
- `idempotent-ttl-seconds = 86400`：`markDone` 时用 `SET` 覆盖，TTL 从 60 秒重置为 24 小时，覆盖用户当天重试。

## 7. 数据库最后防线

| 约束 / 语句 | 防什么 | 防不了什么 |
|---|---|---|
| `uk_reservations_user_request(user_id, request_id)` | 同一请求重复落库 | 超卖 |
| `uk_reservations_active_key(active_key)` | 同一用户对同一时段重复建活跃预约（取消时置 NULL 允许历史留痕） | 不同用户抢同一时段 |
| `ck_slots_reserved_count`（`0 ≤ reserved_count ≤ booking_capacity`） | 计数越界 | 并发窗口内的读改写 |
| `tryOccupy` 的 `WHERE reserved_count < booking_capacity` | 并发下的原子扣减 | 重复提交 |

**唯一索引防重复，CHECK + 条件更新防超卖，两者分工不同，缺一不可。** 容量为 1 的时段被两人同时抢，两条记录 `user_id` 不同，唯一索引根本不会触发。

## 8. 验收

### 8.1 单元测试

| 测试类 | 覆盖 |
|---|---|
| `ReservationGuardTest` | Redis 抛异常时 `tryOccupy` 返回 `DEGRADED`、`release` 不抛异常 |
| `LuaScriptSmokeTest` | 脚本返回码：0 成功 / 1 已满 / 2 已持有 / 0 非持有者释放 |
| `ReservationServiceImplTest` | 编排五个分支（DONE / IN_PROGRESS / FULL / 成功 / 补偿）、状态机、签到、定时任务 |
| `ReservationConcurrencyTest` | 真实 MySQL + 真实 Redis 的并发验收 |

### 8.2 并发测试

前置：`resourceflow_test` 库（结构同 `database/init/1.sql`）、`src/test/resources/application-test.yml`（数据源指向测试库、Redis 用 db 1、开关打开）。

| 用例 | 断言 |
|---|---|
| 闸门开启，30 人抢容量 1 | 成功数 = 1；`reserved_count` = 1；活跃预约行 = 1；Redis `n` = 1 |
| **闸门关闭，30 人抢容量 1** | 同上，且 Redis 无任何 key |
| 同一 `requestId` 并发 10 次 | 落库 1 行；成功返回的 `reservationId` 全部相同 |
| insert 失败（`remark` 超长） | 事务回滚后 `reserved_count` = 0；Redis 占位被删；幂等键被清；同 requestId 可重试成功 |
| 连跑 5 轮 | 每轮都只成功 1 个 |

"闸门关闭"这一条最有价值：开着闸门时 29 个请求在 Redis 就被拦下，数据库只收到 1 个，`tryOccupy` 的条件更新没被并发压过，绿了也证明不了什么。

测试代码的三条纪律：

- 测试方法**不能加 `@Transactional`**：多线程各自开连接，测试方法上的事务对它们不可见，断言会虚假通过。
- **不能 mock Redis、不能用 H2**：mock 掉等于没测原子性，H2 的锁与 CHECK 语义和 MySQL 不同。
- 每个用例前**清库**（`reservation → resource_slot → resource → user`），Redis 只删 `slot:*` 与 `reservation:idempotent:*`，不 `flushDb`。

### 8.3 实测结果

`ReservationConcurrencyTest` 共 9 个用例（30 并发 + 5 轮 + 降级 + 幂等 + 补偿），全部通过，耗时约 12.5 秒。

## 9. 已知取舍

| 决定 | 理由 |
|---|---|
| 不做对账任务 | 短 TTL 模型下计数自然过期自愈，不需要用 DB 校准 Redis |
| 不做熔断/滑动窗口 | 单机项目，一个 `enabled` 开关足够 |
| 不用 Redisson 分布式锁 | 锁粒度是整个 slot，会把并发变成串行，削峰意义消失 |
| 不做 503 快速失败 | 预约场景 DB 扛得住，降级放行体验更好 |
| 不把 Redis 计数当权威 | 允许漂移，DB 才是事实来源 |
| 不手写 `EVALSHA` 回退 | `DefaultRedisScript` 已自动处理 `NOSCRIPT` |

## 10. 配置项

```yaml
resourceflow:
  reservation:
    redis:
      enabled: false            # 闸门总开关，false 时完全不访问 Redis
      slot-ttl-seconds: 300     # 时段占位 TTL
      idempotent-ttl-seconds: 86400  # DONE 状态 TTL
      # processing-ttl-seconds: 60   # 未配置时代码默认 60
```
